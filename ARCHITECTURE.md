## 1. Product in one line

Kairo aggregates sports + calendar + habits into one timeline and delivers a few high-signal notifications (push first; WhatsApp later) instead of notification noise.

## 2. Client strategy

| Surface | Role | Status |
|---|---|---|
| **Expo app (iOS + Android)** | **Primary product** | Build here |
| Next.js `apps/web` | Marketing / App Store landing only | Keep thin |
| PWA as primary client | Retired | Do not revive for MVP |
| React Native CLI (eject) | Not planned | Stay on Expo + EAS |

**Why Expo:** already adopted (SDK 52), EAS Build/Update, Expo Push, Expo Router, Secure Store, and official auth-client paths. RN CLI would cost 1–2 weeks for no product gain.

**Fresh start policy (mobile):** soft reset — recreate a clean Expo Router app shell inside `apps/mobile`, migrate only design tokens, API client patterns, and env wiring. Keep the monorepo, Prisma domain model, Fastify API, and BullMQ worker.

## 3. Backend strategy

| Layer | Choice | Notes |
|---|---|---|
| API | Fastify on Railway | Keep |
| DB | PostgreSQL 16 + Prisma (`@kairo/db`) | Keep domain schema; add auth tables via Better Auth |
| Queue | BullMQ + Redis | Keep; real jobs after auth/onboarding |
| Worker | Separate Railway service | Required before push delivery |
| Cache / rate limit | Redis | Add when routes exist |
| Monitoring | Sentry (later) | After first vertical slice |

## 4. Authentication (decided)

**Provider: [Better Auth](https://www.better-auth.com)** mounted on the Fastify API, with Prisma adapter and `@better-auth/expo` on mobile.

| Requirement | How |
|---|---|
| Google Sign-In | Better Auth `socialProviders.google` (+ optional native idToken) |
| Apple Sign-In | Better Auth `socialProviders.apple` (required for iOS App Store if other social login exists) |
| Email / password | Better Auth `emailAndPassword` |
| Expo sessions | `@better-auth/expo` + `expo-secure-store` |
| App user row | Lazy upsert / link into existing `users` (or Better Auth user + `app_user` profile — see implementation plan) |
| Free tier | Self-hosted — $0 MAU fees |
| Backend setup | Routes on existing Fastify; no second auth SaaS |

**Rejected for MVP:**

- **Clerk** — excellent Expo DX, but another vendor + session model; free tier is fine now, complexity is the issue
- **Supabase Auth** — great hosted auth, but either dual-stack (Supabase JWT + Railway Prisma) or DB migration
- **Firebase Auth** — solid free MAU, weaker Expo-native DX than Better Auth / Clerk
- **Auth.js** — web/Next-centric; poor Expo fit
- **Appwrite** — smaller ecosystem; similar dual-stack tax
- **Hand-rolled JWT-only** (current scaffold) — fine for Google-only; not for email/password + Apple long-term

## 5. Monorepo layout (target)

```
kairo/
├── ARCHITECTURE.md          ← you are here
├── ROADMAP.md               ← milestones & issue alignment
├── apps/
│   ├── mobile/              Expo SDK 52+ (product)
│   ├── server/              Fastify + Better Auth handlers
│   └── web/                 Marketing only
└── packages/
    ├── db/                  Prisma (domain + Better Auth tables)
    ├── core/                Shared zod types / constants (no heavy services yet)
    └── queue/               BullMQ producers + workers
```

Business logic starts in `apps/server` and `packages/queue`. Promote to `packages/core` only when a second consumer needs it.

## 6. API conventions

- Prefix **all** HTTP API routes with `/api` (migrate existing `/auth/*`, `/health`, `/test/*`).
- Auth endpoints live under `/api/auth/*` (Better Auth handler).
- Protected business routes verify Better Auth session (bearer / cookie via Expo plugin).
- `/api/test/*` exists **only** when `NODE_ENV === 'development'`.

## 7. Data model (domain)

Keep the 10 domain tables from the Prisma schema (users, subscriptions, events, user_events, notifications, notification_preferences, habits, habit_completions, connected_sources, ai_copy_cache).

Additions required soon:

- Better Auth tables (user/session/account/verification — generated by Better Auth CLI)
- `user_devices` (Expo push tokens) when notifications land

Link strategy: Better Auth `user.id` is the identity primary key **or** map via `users.auth_user_id`. Prefer one user table owned by Better Auth + a thin `user_profiles` / keep domain FKs on that id — decide in auth implementation PR; do not keep two competing Google-token auth paths.

## 8. Notification strategy

1. **MVP:** Expo Push only  
2. **Later:** WhatsApp (Twilio), Telegram  
3. **AI copy:** templates first; Claude later with `ai_copy_cache`

## 9. Security baseline

- No open enqueue routes in production
- CORS allowlist (dev: LAN + Expo; prod: app + marketing origins)
- Rate limit auth endpoints
- Encrypt OAuth tokens at rest before Google Calendar ships
- Never commit secrets; commit `pnpm-lock.yaml` and Prisma migrations

## 10. What we are explicitly not building in MVP

PWA app shell, WhatsApp, Claude copy, Calendar sync, habits, cricket/tennis/YouTube, Clerk, desktop sidebar, Telegram.
